# 既存OCIのプライバシー・メタデータ監査（2026-11-05）

## 調査対象・実績

公開Docker Hubの既存LTX 2.3 / 10Eros v1.4タグについて、実際のOCI Registry APIからマニフェストとconfig JSONを読み、各レイヤーに対応するビルド履歴を確認した。

監査ログ：[GitHub Actions run 41962503892](https://github.com/open-video-recovery/ltx23-runpod-recovery/actions/runs/41962503892)。

- 15レイヤー、圧縮総容量：約36.52 GiB（configを除く）
- 66件のビルド履歴をレイヤーへ対応付け
- ラベル3件、環境変数、およびイメージ設定を確認
- 約300KB以下の小さいレイヤー10件は、tarのファイル名・テキストを限定的に確認
- **所有するDocker Hubアカウント名、メールアドレス、資格情報の文字列は、検査済みメタデータおよび小型レイヤーでは検出なし**
- 第3・4レイヤーに `/home/...` 形式のパスがあり、第5レイヤーにGitHubリポジトリ参照がある。これだけでは個人情報とは断定できない
- **元のソフトウェア／プロジェクト名を示す独自ラベルと最終ビルド履歴は残っている**。元OCIをそのまま継承する場合、その識別子もGHCRへ引き継がれる
- 第1・7・8・9・10レイヤーなどの巨大なtar内容は全文取得・検査していないため、そこに存在する文字列を否定することはできない

## GHCRへ移すときの注意

- **第7レイヤーは約22.08GiB**で、GHCRの1レイヤー10GB制限を超える。単なるレジストリ間コピーやライセンスレイヤーの追加ではGHCR登録不可。中身を変更せずにレイヤーサイズの再分割が必要。
- ライセンスを追加するだけでは、OCI config内の元のラベル・履歴の値は変更されない。匿名性が重要なら**configのラベル・履歴も確認／整理**した最終イメージを作る必要がある。
- GitHubリポジトリの過去コミットに書かれた元Docker Hub参照先は、後から現行ファイルを変更しても履歴に残る。OCIそのもののメタデータとは別の情報公開経路。
- 公開Workflowの現行版は、元Docker Hubの参照先を **Actions Repository variable `OCI_SOURCE_IMAGE`** から読むよう変更した。トークン・Secretは不要。

## 範囲と限界

この調査はconfig・履歴の完全読取りと、小型レイヤーの限定的なファイル内容検査。巨大レイヤーの全文検査、OS内の全ファイル、過去に生成された別タグやレジストリ上の署名・証明書の検査ではない。

**「直接の個人識別情報が検出されなかった」ことと「匿名性を保証できた」ことを混同しない。** 作業者が含めたラベルやビルド履歴は、最終イメージのconfigで別途確認する。
